# CI fixes: four failures on the first full CI run (2026-10-02)

The first push with the Python-independent OpenAPI schema got further in CI and failed on four tests: one on the Windows engine job, three on the macOS end-to-end job. Each was traced to its cause before anything changed. Two were real bugs in the app, one was a timing bug in the engine, and one was a test-hook bug. No test was weakened.

| # | Where | Cause | Real bug or test issue | Commit |
|---|---|---|---|---|
| 1 | Windows · `test_server` FlowTests: estimate basis `hardware`, expected `precheck` | A coarse clock made a fast pre-check 0.0 s, and 0.0 counted as "no pre-check" | Real bug (engine) | `fix(engine): a pre-check faster than the clock still sets the estimate` |
| 2 | macOS · `shell.spec`: window 1100×720, expected 1280×800 | Atlas asked for 1280×800 whatever the screen; the OS shrank it | Real bug (small): the size was the OS's choice | `fix(app): open the window at a size that fits the screen` |
| 3 | macOS · `results.spec`: 5 × ArrowRight on Shortlist gave 61, not 65 | The popover's late "focus the first control" stole focus after the first press | Real bug (app) | `fix(app): a popover never takes focus from a control the user chose` |
| 4 | macOS · `demo.spec`: clipboard empty after "Copy RA number" | The test's menu hook looked for "Copy RA number"; on macOS the menu says "Copy RA Number" | Test issue (hook) | `test(e2e): native menu picks use the platform's wording and fail loudly` |

## 1 · The estimate on Windows
- **Verified, not assumed.** `time.monotonic` on Windows is `GetTickCount64`, with a resolution of 15.6 ms. The stub pre-check takes about 9 ms: timed with `time.monotonic`, it came out as exactly `0.0` in 15 of 40 runs.
- **Two places then read 0.0 as "missing".** The server chose the hardware guess when `precheck_seconds` was falsy, and `estimate()` required `> 0`. The CLI also rounds the cached value to 0.1 s, so even a precise clock can store 0.0.
- **Fix.**
  - `precheck()` and `Scorer` time durations with `time.perf_counter`.
  - A recorded pre-check counts however fast it was: the checks are now `is not None`.
- **Tests.**
  - `estimate()` with 0.0 and 0.0004 s.
  - The default clocks of `precheck()` and `Scorer` must have sub-millisecond resolution. This is deterministic and fails on Windows before the fix. A first version that timed 30 stub pre-checks was flaky as a regression test, so it was replaced.
  - A server flow where the pre-check takes exactly 0 s on every OS. Before the fix it reproduced CI's failure.

## 2 · The window size on a small screen
macOS shrinks a window that is larger than the screen, and the 1100×720 minimum then holds it. Atlas now chooses the size itself:
- **First launch:** 1280×800, or the primary display's work area (the screen less the menu bar, Dock or taskbar) if that is smaller, never below 1100×720.
- **Saved size:** capped to the work area of the display it reopens on, so a window saved on a big monitor no longer opens larger than a laptop screen.

`shell.spec` reads the work area from `screen` in main and expects exactly that size. Vitest covers a 1920×1040 screen, a MacBook Air, a 1024×768 screen and two monitors.

## 3 · Lost key presses on the cutoff slider
- **The hypothesis was wrong: it wasn't a re-render.** It was tested in the real app: with every preview answering 1.5 s late, all five presses counted and focus stayed put.
- **What happened instead:**
  - Every sheet, alert and popover moves focus to its first control one animation frame after opening (`useModal`).
  - The trace shows the test focused the Shortlist handle 4 ms after the popover appeared and pressed 3 ms later, both inside one frame.
  - On a busy CI Mac that frame arrived after the first press, and focus jumped to the first control, the band handle. The band took the other four presses.
- **Reproduced in the app** by delivering that frame right after the first key press: shortlist 70 → 71, band 55 → 59, focus on "Cutoff band starts at". This is the CI result exactly.
- **Fix.**
  - The late initial focus does nothing when focus is already inside the dialog.
  - `ScoreBand` builds each key press on the value it last asked for, not on the last render, so a press that arrives before the parent re-renders still counts.
- **Tests.**
  - Two Vitest tests: focus is kept, and five presses give 61…65 even if the parent never re-renders. Before the fix they gave focus to the band and `[61, 61, 61, 61, 61]`.
  - A new `e2e/cutoffs.spec.ts` presses keys while every preview answers 1.5 s late and the first frame arrives after the first press. Before the fix it failed with 71 for 75.

## 4 · "Copy RA number" on macOS
- **The app's copy worked; the test never clicked it.**
  - Menus are title case on macOS (Apple's HIG), so the item is "Copy RA Number".
  - The hook that stands in for the native menu looked for the exact label "Copy RA number", found nothing, and silently clicked nothing. The clipboard stayed empty.
  - `results.spec`'s two right-click tests have the same wording problem; they were skipped in CI after failure 3.
- **Fix: the hook, not the app.**
  - Specs keep the source wording, and the hook translates it with the app's own `menuLabel` for the runner's platform.
  - A pick that matches nothing now fails with the labels that were on offer: `no menu item "Copy RA Number" among ["Show details","Move to","Copy RA number"]`, checked by picking the macOS wording on Windows.
  - `copiedText` awaits the clipboard: in Electron 44, `clipboard.readText()` returns a promise.
- **Noticed, not changed:** in Electron 44 `clipboard.writeText()` also returns a promise, and the row menu doesn't await it. The text is still written (checked).
- **The demo also checks why students need attention.** It now compares the engine's failure reasons with the three broken links, not just a count of 3, so a failure here names its cause (see Open below).

## Tests
- Engine: 410 → 413 tests, all pass (1 skipped: OCR).
- Vitest: 188 → 193, all pass. Typecheck, lint and format are clean.
- Playwright: 61 tests, 2 skipped (packaged and installed). The final full run had 60 pass and 1 fail: `perf.spec`'s budget (below).
- The `.venv` on this laptop had lost `httpx`, which the FastAPI test client needs. It was reinstalled from `engine/requirements-dev.txt` (already approved; no new dependency).

## Open (not changed)
- **`perf.spec` "live cutoffs answer within 200 ms" fails on this laptop in the full suite.** The test allows 300 ms for the slowest of eight presses, and the first press after opening the popover takes about 275–310 ms here (CI's macOS run: 286 ms). This is not caused by these fixes: an A/B with and without fix 3 gave 274–294 and 296–318 ms. The budget was left alone: loosening it would weaken the test. It's worth a look as a performance task: the first two answers are about 3× slower than the rest.
- **`demo.spec` once had 4 students needing attention instead of 3,** in 2 of 7 full local runs, both early in the session.
  - It never happened in 12 runs of the demo alone (four of them with the engine suite loading the CPU), and the failing runs' engine logs were not kept.
  - The failing runs took about 20 s longer than usual, which looks like a network timeout around the simulated outage.
  - If a download timed out during the outage and the probe then found the stub back, that student would be failed as "retryable" instead of the run pausing. That is a rule-5 question, not yet confirmed.
  - The demo now names the failure reasons, so the next occurrence (local or CI) will say which it is.
